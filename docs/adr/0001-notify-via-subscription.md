# 通知解耦为订阅模型

原设计在任务定义（ScheduledTaskCreateRequest）内携带 notification 块。决定：通知策略从任务创建协议中剥离，调度服务提供独立的订阅接口——订阅方登记过滤条件与回调端点，调度事件与执行结果以事件（Event）形式推送，通知渠道与通知效果由订阅方自行实现。

理由：任务创建与通知消费解耦后，新增通知渠道或调整通知策略不改动调度协议与已有任务定义；调度服务只负责事实（Event）的产生与分发，不承载通知语义。

## Considered Options

- 在任务定义内保留 notification 块，由调度服务内置通知能力：协议与通知逻辑耦合，渠道扩展需要改任务协议、迁移任务定义。
